# Next Reader: one pass

This is the short working checklist for the next Reader. The [release runbook](READER_RELEASE_RUNBOOK.md) remains authoritative. There is one publisher, one draft PR, one independent editorial/source/privacy acceptance, one owner publication decision, and the existing Netlify deployment. This checklist creates no new gate.

## Reader design contract: identity without sameness

For Reader #69 onward, preserve the approved GhostMesh identity without cloning the preceding article's composition. Reader #68 is a useful standard for substantive opening, illustration, visual pacing and source polish, **not** a mandatory page layout. Readers #63 through #68 remain a reference collection; select the strongest source-appropriate precedent and explain the choice in the existing PR.

| Design authority | Rule |
| --- | --- |
| **Fixed site shell** | Reuse the accepted branded header/footer, navigation, search, sharing, appearance control and functional scripts/styles. Preserve responsive and keyboard behavior. Do not recreate the shell inside a Reader or replace it with a minimal imitation. |
| **Consistent reading contract** | Maintain readable measure and contrast, typography relationships, accessibility, source provenance, evidence limits, source/cue navigation when applicable, and the existing catalog-backed Reader and separately classified SharePlane relationships. Both themes must work. |
| **Adaptable editorial vocabulary** | Choose source-appropriate layouts, accent treatment within the established palette, visual rhythm, evidence comparisons, callouts, timelines, diagrams, figures and source-ledger presentation. Reuse existing patterns when they fit, but avoid a repeated three-card formula. |
| **Open creative direction** | Allow a distinctive narrative composition, visual metaphor, original illustration or interactive explanation where it makes the subject clearer. A prose-led Reader may need no custom infographic. No visual may overstate evidence, replace required text or impair reading. |

Make five decisions inside the existing editorial/Creative Lock work, not a separate approval form: **thesis**, **why this matters to the reader and GhostMesh**, **visual concept**, **one or two signature treatments (or none)**, and **approved precedent/components to reuse**. Give a short rationale for anything genuinely novel. The manuscript, source map, claims, relationships and public-safe boundaries remain owner-controlled; an implementer does not invent them.

Design to the argument: technical investigation may need annotated measurements; conceptual analysis may need restrained editorial typography; system architecture may need a dependency map; contested claims may benefit from side-by-side evidence. These are examples, never compulsory templates. Prefer a few meaningful changes in scale, density and whitespace over repetitive cards or unformatted bullet lists. Use actual HTML links rather than pasted URLs, and keep headings, body text, captions and source notes distinguishable in light and dark modes.

Compare the **shared shell** to the chosen approved precedent for fidelity, and the **article body** to its own visual concept for distinctiveness. One consolidated desktop/mobile review covers both. Preserve the existing independent editorial/source/privacy acceptance, CI, exact-head owner approval and Netlify verification. No new generator, framework, component service, reviewer, release stage or retroactive restyling is authorized by this contract.

## Before implementation

- **Select a baseline per Reader.** Any already published, owner-accepted Reader can be the presentation/editorial starting point, including #65 or #66. Choose based on the new source's actual editorial and visual needs, not the highest Reader number. Record the selected baseline and which layout components are intentionally reused or changed in the existing PR. The baseline is a reference, not an immutable template or a second approval contract. Keep the shared source/privacy, catalog, relationships, accessibility and release requirements. Do not copy another Reader's source-specific claims, cues, media, links, hashes or evidence.
- **Start from canonical GitHub.** Fetch the current default branch, inspect open PRs and live publication state, and work in a fresh checkout/worktree or verified-clean synchronized branch. Never assume an older local copy is canonical. Identify the active publisher and avoid competing edits to the same Reader.
- Qualify the exact source and retained private aids. Record honest acquisition, coverage, transcript/caption method, SHA-256 digests and limitations. Never commit media, full transcripts, captions, private paths or signed URLs.
- Lock the complete original manuscript and presentation together, adapting depth, layout and visuals to the source.
- **Reader #68 regression lesson:** Before the first draft PR, copy the accepted Reader shell components intact: branded header, GhostMesh lead-in with three styled moves, opt-in source player, chapter-card grid, reading rail, evidence/source treatment, methodology, share actions and branded footer. Copy the matching component CSS, responsive overrides, color tokens and scripts as well as the markup; a generated header/footer with missing styles is still a broken wrapper. Compare the rendered header and footer directly against the selected accepted baseline at desktop, tablet and phone widths in both themes. Preserve the established evidence hierarchy, readable relationship titles and source-role distinctions; prefer an ordered, ruled source ledger over generic hyperlink tiles. A minimal custom shell or raw timestamp paragraph is not equivalent. Verify a real desktop screenshot from top through footer and one narrow mobile screenshot before calling the presentation coherent. This is an implementation quality check within the existing pass, not a new approval gate.
- Complete the **entire** claim/cue register before layout, including unsuccessful contenders and first-pass failures. Map every source claim to its timestamp and explicitly distinguish creator report, private caption aid, manufacturer specifications and independent verification. Complete both relationship decisions: catalog-backed Readers and independently labeled SharePlane Works, with specific rationales or justified zeros. Settle the public-safe receipt wording before rendering.

## One implementation pass

1. Stage the locked authored HTML, catalog record, source map and sanitized provenance together. Check the page title, metadata description and source identity against this Reader, not its chosen baseline. Reuse existing wrappers, projectors and **canonical destination URLs** from approved catalog records; verify actual video chapter links and their timestamp formats. Do not introduce a new page builder.
2. During the draft pass, run `python3 scripts/generate_site.py`, `python3 scripts/knowledge_contract.py`, the focused tests, and `git diff --check`. The full `make reader-prepare` target includes the publication/editorial gate; run it after independent acceptance is recorded, not as a prerequisite for that review.
3. Open the single draft PR for hosted preview once the initial mechanical candidate is coherent. Review the rendered manuscript against the locked original for omissions, reordering, source/claim meaning, links and disclosures. Inspect that preview at desktop and 320/390/430px mobile, including navigation, timestamps, keyboard, dark appearance, video thumbnail/fallback and console health.
4. Obtain independent source/editorial/privacy acceptance **once the authored article, claim map and evidence posture are stable, before asking Tony to publish**. Record real findings in existing `content/editorial-reviews/` and `content/editorial-depth/` formats. Apply any `REVISE` findings as one focused correction set; re-review only changed inputs. Bind the receipts and rerun `make reader-prepare` before final owner UAT.
5. Commit the reviewed candidate to the existing **draft** PR. Confirm remote head, hosted CI, Netlify preview and owner UAT. Request one explicit publication approval for the reviewed candidate; do not merge before it. The normal full hosted gate remains authoritative.
6. **Reconcile the actual release state before asking for help or declaring HOLD.** Read the current PR head, CI, latest timestamped comments/receipts, recovered source custody, recorded reviews and the live site. Older PR descriptions and draft-stage `Remaining` lists are not current-state evidence if later receipts supersede them. Update the PR status summary when a hold is resolved; state any genuinely missing requirement precisely.
7. **Carry forward owner authority.** Once Tony explicitly approves publication of the reviewed candidate, routine ready-for-review, exact-head merge and existing Netlify deployment need no repeat approval. A presentation-only CSS adjustment that preserves the accepted manuscript, source/privacy claims and relationship decisions does not automatically invalidate editorial approval. If the head changes, verify the exact diff and affected checks; return to Tony only for a material editorial/source/privacy change, failed required gate, explicit hold or altered approval scope. A technical receipt must not be misrepresented as an additional owner editorial decision.
8. After an authorized merge, independently verify `main`, the live article, player, chapter seeks, public receipt, catalog, both relationships, sitemap and source privacy. Record merge SHA, live HTTP result and expected content/layout markers in the existing PR/issue before closing the issue. A green preview or merged PR alone is not publication proof.

**Stop only for a real change or failure:** material editorial/source revisions, invalid privacy/custody, failed checks, changed approved content, or owner hold. Do not introduce a PREPARE approval, second publisher, repeated source qualification, extra orchestration service or postmortem-specific validator.
