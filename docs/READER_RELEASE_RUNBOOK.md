# Reader release runbook

This is the one publication queue and release path for `pinklon/ghostmesh-readers`. One accepted publisher owns a candidate from source handoff through the final production receipt. Source custodians and independent reviewers can supply evidence or read-only findings; they do not start competing uploads. The public repository contains original analysis and sanitized receipts, never copied media, captions, full transcripts, private source packs, signed URLs, or credentials.

## Canonical queue and evidence

The status table below is the one maintained Reader queue. Add a row when a source is accepted; update its public-safe evidence status or receipt reference, exact candidate head, review gate, PR and deployment state as work advances. The publisher's task receipt holds detailed evidence for these fields, not a second status queue. Keep private custody in private storage and cite only sanitized evidence in public Git. Do not create a second tracker or uploader.

## One bounded release

1. Qualify the exact source in private custody. Preserve video identity, original timestamps and native aspect. If transcript, audio or frames are incomplete, narrow public claims and name the limit. Keep source files outside this Git history.
2. Author the canonical three-part brief, recommendation, dated claim register, counterevidence and sanitized receipt in `content/`. Review every existing Reader for substantively supported typed graph routes; record rationale for links or none. Run `python3 scripts/generate_site.py` and `python3 scripts/knowledge_contract.py` once from the final inputs. Batch all generated public files into the same local commit and use the repository's normal authenticated Git push. Do not loop over individual Git-tree uploads.
3. Run `python3 scripts/generate_site.py --check`, `python3 scripts/knowledge_contract.py --check`, `python3 scripts/check_site.py`, the full Python tests and `git diff --check`. Check desktop/mobile, opt-in playback, source timestamps, link targets and the public/private boundary. Record selected cues, sections and claims as public-safe paraphrases in `content/source-maps/<slug>.json`. Retain the actual independent editorial/agent findings and limitations in `content/editorial-reviews/<slug>.json`, and make the underlying task report available for Tony to inspect. These candidate-authored files are evidence for his decision, not machine-authenticated proof of an agent’s identity. After opening the candidate PR, set `ownerDecision` to its PR number with `commentId: null` and calculate the single exact line from `scripts/editorial_depth.py`’s `acceptance_marker(receipt)`. Tony evaluates the actual findings and article, then posts that line as his own GitHub PR comment, without the Codex connector. The marker binds the PR number, source identity and private-aid digest, source cue map, retained findings, authored article, evidence and full assessment. Record the comment ID in `ownerDecision` and rerun exact-head CI. The validator fetches the GitHub comment and PR, requires the `pinklon` owner account, no GitHub App mediation, the exact marker, and identical creation/update times. It checks the current CI PR number for an open candidate; after merging, it checks the immutable merge commit for the accepted article, Reader binding, receipt, cue map and findings. Editing or deleting the comment, changing bound bytes, or referencing a different PR fails closed. This is an authenticated owner-account decision and tamper-evident record; code cannot prove who physically typed it, verify private agent identity or determine source truth. If only generated projections or presentation metadata change, retain acceptance while all editorial bindings remain identical.
4. Push the exact local commit to its named public review branch once authorized. Verify the remote ref equals that commit. Open one draft PR. Use the normal GitHub checks and Netlify deploy preview; inspect the exact head, page, catalog, map, sitemap and source privacy. A green preview is a review surface, not production proof.
5. Merge only the owner-authorized exact head after review, CI, preview and normal repository protections pass. If the head or base changed materially, reconcile before merging. Verify `main` and the Netlify production page, original player and timestamps, content, source links, receipt, catalog count, map edges, sitemap and private-source exclusion. Record the PR, reviewed head, merge SHA, tests and complete live URLs in the final receipt.

## Denied or uncertain operations

If a push, PR, merge or deploy is denied, stop that operation. Report its exact target, checker reason, known execution state and unaffected completed work. Seek a decision for that specific operation through the normal approval path; do not change credentials, permissions, routes or service settings, and do not repackage the same write through a connector. When materially new authorization arrives, check the remote state first and attempt only the denied operation once. If a write times out or disconnects, read back the remote ref or object before deciding whether any retry is appropriate. Do not treat an absent status message as proof of failure.

This runbook does not authorize any new Reader, merge, deployment, private-source disclosure, ReasonPack operation or historical PR 31–34 promotion. Unrelated PR 27 provenance work is not a prerequisite for a source-qualified Reader.

## Proportionate editorial depth

The reviewer first states why the source calls for a brief or extended treatment. A long source, many material claims or a consequential architecture recommendation requires extended mapping. A short or thin source can support a concise article. There is no universal word or citation quota. In either case the reviewer assesses faithful source coverage, the strongest argument, assertion versus observation versus inference, serious counterargument, assumptions and failure modes, a falsifiable test, and an original GhostMesh synthesis. Performance, economics and threat governance are assessed when relevant; a `not-applicable` decision needs a reason. Source timestamps and claim IDs map the analyzed material. An unresolved blocking gap means `revise` or `hold`, not acceptance.

`content/editorial-depth.schema.json`, `content/source-map.schema.json`, `content/editorial-review.schema.json`, `scripts/editorial_depth.py` and `scripts/check_site.py` enforce the receipt structure, separate cue/claim map, retained findings hash, status, private source-aid SHA-256 and authored article/evidence bindings before a changed Reader can enter the normal release path. An unreachable, edited, connector-posted, wrong-PR or wrong-hash owner comment fails release. Human independent review remains real but its private-task identity is not authenticated by CI; Tony takes responsibility for evaluating those findings before his separate exact-content acceptance. Production merge/deployment remains a later owner decision. The fixed `content/editorial-depth/legacy-policy.json` admits exactly 26 byte-identical historical Readers already public at the adoption baseline; it makes no retroactive qualitative claim and cannot cover a revised article. Do not update that baseline to avoid review.
