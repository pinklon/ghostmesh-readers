# Scout Research Library: content-only tranches

The canonical public register is `content/scout-research.json`. The generated searchable catalog is `/scout/research/`. The earlier `/scout/archive/` and `/scout/essays/` addresses remain stable.

1. Secure Tony's editorial approval of the complete public Markdown or static essay, evidence boundary, provenance, topic tags and any exact related-work IDs, except for the narrow routine source-report class below. Do not export private Scout scans or internal experiments.
2. Put reviewed source content at its existing stable location (`content/scout/reviews/<id>.md` for investigations; `site/scout/essays/<slug>/index.html` for legacy essays). Future essays should use the existing public essay layout and its canonical trailing-slash URL. Never silently rewrite published text.
3. Add one `published` entry to `content/scout-research.json`. Set a unique stable ID/slug and exact source path. Add only owner-approved `relatedIds`. For new publications, add the dated explicit first-release event to the release ledger before entering its ID in `releaseEventId`. The six historical essays were public by October 23 according to the merged nine-work Library PR and production-verification inventory, but their exact first-publication days remain unverified. Their `publicByOn`/`publicByEvidenceUrl` fields preserve that bounded fact; their null event IDs do not create retroactive RSS announcements. New records cannot use this exception.
4. Run `python3 scripts/generate_site.py`, `python3 scripts/generate_site.py --check`, `python3 scripts/check_site.py`, and `python3 -m unittest discover -s tests -p 'test_*.py'`. Check the generated index, links, sitemap and absence of private files.
5. Review a Netlify deploy preview on desktop/mobile. Tony approves semantic/visual UAT and the exact PR head before merge except for the narrow routine source-report class below. Verify production HTTP routes and Netlify deploy ID afterward. Keep unknowns UNKNOWN.

No database, semantic-autolinker, reader rewrite or ingestion job is needed. Public research inventory and historical private Scout candidate counts must remain separate until independently reconciled.

## Repeatable public handoff

- Classify the approved work as an investigation, essay, experiment, counterexample, method, journal or narrow source report. Use the existing Scout review template for investigations, the Scout essay wrapper for original essays, methods and source reports, and the existing journal route only for the journal. A Scout-origin Reader remains a Reader unless separately admitted to this register; never duplicate its article to inflate the research count.
- Keep one canonical `published` record per public work in `content/scout-research.json`. That record drives the Research Library, recent-research navigation and the Scout relationship projection at `/scout/research/relationships.json`. The Scout graph is discoverable from the Library, the Reader map and `/.well-known/ghostmesh-knowledge.json`; the Reader graph's node and edge counts remain separate. `relatedIds` are owner-approved public research IDs only. The projection must contain every approved link, use `scout:`-prefixed graph IDs, and expose no private or under-review records. An HTML link alone does not satisfy the graph check.
- Add a source-bound, stable release event for a new public work or material revision when the actual release date is known. The generator updates RSS and sitemap from the same approved records and event ledger. A build, private research run or routine copy correction creates no event.
- Present first-publication dates from the accepted release event, review dates from `reviewedOn`, and a conservative `Public by` bound for the six evidenced legacy essays. Never substitute an authored, reviewed, commit or later update date for first publication. Keep the date label in the Research Library, essay index and essay hero outside the locked article body.
- Run the existing generator, stale-output check, site gate and tests. Review both the rendered links and machine-readable Scout graph on the exact preview head; verify canonical URLs, RSS uniqueness, sitemap and no candidate `noindex` on the release candidate. After an exact-head owner merge decision, or a qualified standing source-report merge, read back the production deployment and those same live routes. Do not infer success from a green source test or a Netlify preview alone.
- Page counts and recent work derive from the public register. Historical prose retains its original dated context; a current library link can explain that context without rewriting an accepted article. Editorial claims, new relationship choices, artwork and exact release authorization remain with Tony.

### Daily run disposition and release proof

- For every retained finding, report one outcome in the existing run handoff: already published/duplicate with its canonical URL, a qualified routine source report, a non-routine public-copy candidate, or an explicit hold with the missing source, review or permission. Collection observations alone are not publication candidates. This is a handoff record, not a new queue or an automatic semantic verdict.
- Before any public-copy handoff, name the source version and original date, check the latest revision or successor, record why older evidence remains relevant, and separate source-reported behavior from an executed observation or account entitlement. Apply the six-month disclosure below when it is triggered. The independent reviewer must accept the exact source-bound copy; tests cannot establish the truth of a capability claim.
- Classify the work before release. Only `routine-source-report-v1` receives standing release authority. Essays, interpretations, recommendations, uncertain capability claims and new relationships retain the ordinary owner decisions. A later revision keeps the same canonical record and adds a material-update event only when the actual public revision is released; it does not create a second work.
- The register and release ledger project the Research Library, Scout landing, relationship JSON, sitemap and feed. The older `/scout/essays/` page is a curated static index; if it carries a revised work, its card title, summary and source scope must match the canonical record on the exact candidate head. An approved Reader link on an essay is ordinary related reading unless separately admitted to the Scout-only relationship graph.
- After the qualified unchanged-head merge, read back the actual Netlify production deploy and live canonical article, Library card, relevant curated index card, approved links or graph edges, sitemap, unique feed event and public/private boundary. A passed source test, preview or merge alone is not a live publication receipt.

## Source freshness at selection

- Record the source's original publication or applicable version date separately from the day Scout found, inspected or published it. Before selecting a finding, inspect the primary source's latest revision and any successor or superseding document. Identify which version supports each material claim; a current retrieval date does not make old text a new development.
- If the relevant source is more than six calendar months old at review, it may still be selected. The public page and card must visibly say **Older but relevant**, give the original source/version date, explain the current question that makes it worth revisiting, and link or describe the latest revision/supersession check and any material difference. Do not present resurfacing as a new announcement. If the source date or current applicability cannot be established, keep that uncertainty explicit and hold routine publication for ordinary editorial review.
- Preserve the distinction between a newly announced change and older evidence newly relevant to a current question. Do not use an age cutoff to discard a useful source, and do not infer that an older version's rules still govern a newer one. The independent reviewer checks the dated source, current applicability, public label and reason for resurfacing before accepting a release.

## Standing release: routine source reports only

Tony approved a narrow standing production policy on October 26, 2026. It applies only to a new `source-report` record with `standingRelease: "routine-source-report-v1"`. Use ID `report:<slug>`, the existing `/scout/essays/<slug>/` static wrapper and the normal public release event. This is a source-reported observation, not a rated product investigation, GhostMesh recommendation, executed test, entitlement finding or original essay. The page must visibly say **“Source-reported; not independently tested”**, link the exact public primary source, and show the observation date. Use an official release note, official documentation or primary repository; retain the source URL and inspection limits. No new relationships may be added through this standing class.

An independent reviewer, distinct from the publisher, must inspect the exact public page, Library card copy, feed summary and primary source and write `content/scout/release-reviews/<slug>.json` with schema `ghostmesh-scout-source-report-review-v1`. The receipt binds the source-page SHA-256, exact record `title`, `summary`, `evidenceLimits` and `topics`, source URL, observation/review dates, inspection method, reviewer and publisher task identities, an `accept` decision, and affirmative checks for source-only claims, no new recommendation, no execution or entitlement claim, and public-safe copy. The feed title and summary must match that reviewed record. The validator checks this binding and the visible public wrapper; it cannot itself establish that a source claim is true or that the reviewer exercised good judgment. If any review check fails or source authority is uncertain, stop and ask Tony.

For a qualifying record, the existing sole publisher may prepare the release event and all deterministic site projections, push one scoped PR, run the existing hosted CI, inspect the Netlify preview on desktop/mobile, and merge the unchanged exact head under this standing authorization **without a fresh generic owner approval**. Before merge, confirm the branch is current and run `python3 scripts/check_scout_routine_release.py --base <current-main-sha>`; the existing hosted site-check also runs that guard on PRs. It requires exactly one additive report, one new stable event, unchanged earlier records/events and only the report, receipt, register/event entries and expected generated projections. Verify canonical URL, correct wrapper, date, RSS uniqueness, sitemap, Research Library and public graph, no private data, and no release `noindex`. After merge, verify the Netlify production deployment and those same live routes. Stop on drift, failed checks, missing reviewer acceptance, wrong wrapper, uncertain source, or any protected action denial; do not force, bypass or retry an uncertain merge blindly.

Essays in Tony's voice, new interpretations or recommendations, performance/security/availability or account-entitlement claims, experiments, disputed evidence, private-source disclosures, artwork and new relationship choices remain under the ordinary semantic/visual acceptance and exact-head release decision. A routine source report that grows into any of these leaves the standing class. The standing policy creates no new collector, inference service, account access or publication queue. Roll back a bad release through the existing repository revert and Netlify deploy path, preserving the release receipt and publishing a correction when subscribers may have received the item; do not silently rewrite history.
