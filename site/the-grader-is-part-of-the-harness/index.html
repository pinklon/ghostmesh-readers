The Grader Is Part of the Harness

Two papers show agents improving the procedures around model calls. Cloud Codes asks whether the durable skill is writing a harness or designing the feedback that tells an agent what to improve.

Reader brief

What the video is about

Cloud Codes compares two research efforts that let an AI system revise its own working procedure, then argues that evaluation design determines whether this feedback helps.

Why you should care

Useful for teams tempted to treat an adaptive agent harness as a reusable product recipe. The reported gains are real author results on specified tasks, while coding transfer is mixed.

What GhostMesh takes away

Treat a proposed harness change as an experiment with a named grader, held-out tasks and a rollback path. Do not promote a self-judged gain into production authority.

What actually changes

The video starts with failed attempts to handcraft agent harnesses, then turns to two research approaches where a model changes the executable procedure around another model. In Harness Learning, a proposer edits a solver’s program using execution feedback. Its weights stay fixed during test-time adaptation. In MASS, a model works through solver, optimizer and evaluator roles, searches for better multi-agent workflows, then trains on the resulting trajectories. Neither paper says that an arbitrary agent should rewrite a production workflow without boundaries.

The title's provocation is useful if read narrowly. A harness is code and information flow, including tools, prompts, routing and termination. Its shape matters. But an adaptive loop can optimize only what its feedback represents. The operational skill is therefore to define the task, its grader and its failure boundary before treating the loop as improvement.

The 4B versus 35B result

At 02:27, Cloud Codes introduces the Harness Learning paper. The authors train a smaller proposer on harness revisions, including reinforcement learning from task outcomes. On 21 unseen Reasoning Gym families, its mean single-revision score is 0.62, compared with 0.56 for its 35B teacher under the same protocol. The base proposer scores 0.32. That supports transfer of revision skill within the tested task family.

The teacher still does better when an oracle selects its best of eight candidates. The tasks are puzzles and multi-hop questions, not a production coding-agent deployment. Treat the result as an interesting method and a specific measured comparison, not proof that a smaller model is generally a better engineer.

The MASS transfer test

At 04:51, the video moves to MASS. The authors report 1.20 to 1.60 times the base score per output token on four open-ended research benchmarks after two cycles. That is a meaningful reported efficiency result within their test design. The same team reports 0.96 times on Terminal-Bench 2.0 and 0.94 times on SWE-bench Verified. Those coding results sit below the base value, so this paper does not justify expecting a coding gain from the published loop.

The evaluator in MASS is also model-driven. A model that proposes and grades its own work may discover better routes, but it can also settle on a convenient proxy. The paper's structural constraints and public benchmark checks matter precisely because self-assessment alone cannot certify the output. The Sakana explanation is from the same authors' evidence family, not an independent replication.

The missing production test

From 08:06, the narrator argues that graders are the bottleneck. GhostMesh agrees with the design concern as an inference, with a sharper boundary: a grade must measure the user-visible result and any forbidden action, not just the elegance of the harness or the model's self-report. Anthropic's evaluation guidance makes the same practical distinction between a task and a grader; it does not validate either paper's reported gains.

For a bounded experiment, freeze a small holdout set with real failure cases. Record task success, wrong answers, tool misuse, cost, latency and human intervention. Keep the proposed harness inside a sandbox, review the diff, and make rollback possible. A candidate that raises a self-generated score while failing the holdout is not an improvement. Nor do these papers establish that an automated grader can replace judgment about security, legal or customer impact.

What to do next

If your agent repeatedly fails a named task, test whether a harness change helps before rewriting the model or adding more agents. Use the same baseline and holdout for both. If gains disappear on a changed format, if the grader misses a harmful action, or if coding performance regresses, keep the old procedure. The video is worth watching as a research map. Its conclusion becomes a deployment rule only after a task-specific evaluation that someone other than the optimizing loop can inspect.
