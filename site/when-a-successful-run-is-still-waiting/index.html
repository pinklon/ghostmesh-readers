When a Successful Run Is Still Waiting

On October 23, LangChain clarified that success in a LangGraph API webhook can include a run paused at interrupt() for human input. The payload omits the interrupt; thread-state inspection is needed. [C1] A documentation change can reveal an integration risk without establishing a product defect. In this case, a consumer that translates the event directly into “the task is finished” would be making a stronger claim than the event supports.

01 / Analysis

The event is not the outcome

The source is written developer documentation about run callbacks, not a video or an incident report. It matters to anyone who uses an execution event to close a task or trigger a consequential next step. An interrupt can request ordinary information as well as approval; waiting for human input does not itself describe an authorization decision.

Verdict: Worth studying. The GhostMesh takeaway is to audit the existing consumer’s completion rule before adding orchestration. Preserve the event’s identity, inspect attributable state and keep uncertainty visible. The proposed checks below are analytical recommendations, not measured results.

The status can be coherent as a description of run processing without certifying the user’s outcome. There is no evidence here of an actual integration mistake or bypassed human approval. Nor does a documentation update establish when the behavior began. What it supplies is a concrete question for review. Where does the receiving application convert a runtime status into a completion claim? The useful investigation starts at that conversion, before proposing a new orchestration layer.

02 / Analysis

Define what the consumer is allowed to conclude

Consider a hypothetical workflow that prepares a report, waits for review, then delivers the approved version. The preparation step and the delivery step can both leave useful records, but they answer different questions. A notification about execution should not become evidence that the recipient received the report. The consumer needs a completion condition defined in terms of the requested outcome, and it needs to know whether the evidence it has actually satisfies that condition.

The rest of the webhook contract reinforces that distinction. A cancellation before execution produces no callback. A thread can receive callbacks for different runs. The payload’s values represent its latest checkpoint state. [C1] None of those facts is inherently a failure. Together, they make “one thread, one terminal notification” an unsafe assumption for a consumer that has not checked the contract.

The first proposed change is deliberately small. Keep the incoming event as an observation, preserving its run_id and thread_id. At the existing continuation point, retrieve the state needed to decide whether the work is waiting, has reached its declared outcome, or remains unresolved. Where a checkpoint or version is available, use it to establish attribution. Do not quietly substitute whatever the thread happens to contain now for evidence about the run that triggered the event. [C2]

This readback is not a cure for concurrency. A newer run may have advanced the thread before the consumer examines it. The inspected documentation does not establish an atomic pairing between callback delivery and the subsequent state read. If the application cannot demonstrate that the state belongs to the decision it is making, the honest result is UNKNOWN, not an optimistic terminal label. That requirement is an engineering inference, and its feasibility depends on the deployed API and retained records.

Silence requires equally careful treatment. A missing event cannot establish success or failure by itself. If an existing workload already records the run it expects to finish, a bounded reconciliation step can inspect that run when its expected receipt is missing. This does not call for a new perpetual polling service. It calls for an explicit unresolved state and a responsible next action, so that missing evidence neither fabricates completion nor strands work indefinitely without examination.

03 / Analysis

Keep the completion rule separate from permission

An event consumer might classify a report as ready for review and still lack authority to deliver it. That separation matters during handoff. A successor worker should inherit enough identity to recognize the same intended operation, but inheriting a work record should not renew an expired approval. Before a new external effect, the executor must check the current authorization for that destination and payload. The operation can remain the same while the answer to “may it proceed now?” changes. [C4]

These are established continuation concerns, not discoveries introduced by the webhook page. Temporal’s documentation says completed Activities are not rerun during replay, while an Activity that never reports back can be retried. LangGraph’s Functional API documentation similarly describes rerunning unfinished tasks. [C3] A durable execution history therefore cannot, by itself, settle whether an external destination accepted an action before its acknowledgment was lost.

AWS’s account of idempotent APIs supplies a useful boundary. A caller-provided request identifier distinguishes a retry from another intentionally identical request; changed parameters under the same identifier can be rejected. The service must couple token recording with the mutation, and its retention window matters. [C3] These are destination contracts, not properties created merely by writing a local receipt.

For the proposed consumer, keep the stable operation identifier and its payload binding across worker replacement. Record uncertainty when the destination outcome cannot be established. An uncertain effect must stop automatic replay unless an applicable, verified destination contract makes the retry safe. Otherwise the next step is reconciliation or an accountable decision, not a new worker guessing that an absent acknowledgment means an absent effect. A local ledger helps explain the decision; it does not make two separate systems commit atomically.

04 / Analysis

Test the interpretation rather than another orchestration stack

A useful first experiment needs no live account, model call or production mutation. Create a disposable event reducer with a fake state reader and a fake destination. Its inputs are synthetic callbacks, run records and checkpoint snapshots. Its output is a proposed classification and, where permitted, a proposed next action. The purpose is to test whether a small consumer contract prevents overstatement, not to certify LangSmith, Temporal or any deployed system. This experiment has not been run. [C8]

Begin with a callback labeled success paired with a pending interrupt. The expected classification is WAITING, with no delivery action. Next, represent a run canceled while pending and deliver no callback. When the existing workload’s reconciliation point is reached, the consumer must inspect the run or retain an explicit unresolved state. It must not manufacture a completion receipt from elapsed time.

Then deliver the same callback twice and delay run A’s callback until run B is waiting or complete. The consumer must not apply A’s event to B or multiply a proposed effect. Return an unattributable checkpoint, then make the state reader unavailable. Both cases must remain UNKNOWN. These are proposed stress cases, not observed bugs. [C8]

An always-unknown classifier would pass those safety checks while accomplishing nothing. Add an attributable completed read-only task that must become COMPLETED, without demanding a nonexistent destination-effect receipt. A temporary read failure must resolve at the next declared reconciliation opportunity when valid evidence arrives. Compare false completions, false waits, unresolved cases and handling effort with the current consumer. Authorization and effect-receipt checks apply when the next action requires them, not to every callback.

Keep the falsifier concrete. One false completion, one cross-run attribution, one unauthorized proposed effect or one duplicate proposed effect is enough to reject the reducer’s current rules. A legitimate waiting state mislabeled as terminal also fails. Passing those fixtures would justify reviewing the actual integration boundary, not claiming an exactly-once system. The next evidence needed would be version-specific API behavior, destination guarantees and a controlled end-to-end test under separate authorization.

05 / Analysis

Prefer the smallest change that preserves the distinction

The strongest objection is that an audit may find no misinterpretation in the existing consumer. No GhostMesh defect or need for an adapter has been established. Mature workflow systems already have interruption, retry and history mechanisms; an independent ledger could create competing truth and harder recovery. First inspect what the existing runtime retains and exposes. Add only missing classification and evidence checks. If an adapter grows into a scheduler, policy engine or competing lifecycle, reassess the design before building it.

There is a smaller version of the same reasoning in document ingestion. Docling’s inspected Markdown serializer flattens certain distinct header structures into the same visible labels, while a structured export retains information the projection cannot express. [C5], [C6] This is an intentional format tradeoff, not evidence of an OCR defect; ordinary prose retrieval may benefit from the simpler text. Where structure matters, the cheapest intervention may be to preserve a distinction already recovered rather than add a parser downstream to reconstruct it.

The webhook case deserves the same restraint. Keep the original event, establish which state it can speak for, and make the completion claim no broader than the evidence. Preserve operation identity without treating it as permission. When attribution or outcome remains uncertain, leave that uncertainty visible to the next authorized actor. The result sought is a consumer whose decisions can be checked at an existing boundary, not another system that claims to own the work.
