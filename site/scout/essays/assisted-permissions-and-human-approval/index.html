Assisted permissions and the meaning of human approval

The important question in GitHub Copilot's assisted-permissions release is not whether an agent can interrupt its operator less often. It is whether a team that writes ask into its policy still means ask a person.

GitHub announced general availability across Copilot CLI, the Copilot app, and Visual Studio Code on October 26, 2026. The announcement describes model-based approval of requests judged safe, with other requests referred to the operator. Administrators can restrict Assisted and Allow All independently. That is a meaningful alternative to an all-or-nothing approval choice. It is not, by itself, evidence that an organization's human-signoff requirements survive unchanged. GitHub announcement

What the policy actually promises

The assisted-permissions guide says eligible CLI enterprise ask rules for shell commands, file reads, file writes, and URLs can be satisfied by model approval. Denials remain in force. Sandbox-bypass requests and other enterprise-mandated tool approvals are outside this review. Assisted permissions

The enterprise reference, however, describes permissions.ask as requiring fresh human approval and says approval shortcuts cannot satisfy it. These descriptions are in tension. A careful reading should preserve that disagreement rather than silently selecting the more reassuring interpretation. This is a documentation finding, not a demonstrated enforcement defect. Enterprise permission rules

Version history matters. VS Code 1.142 warned against combining Assisted with granular permission rules. The newer 1.143 notes say Assisted no longer asks again for eligible managed requests it approves, while retaining one-time limits, denials, and sandbox restrictions. The older warning should not be repackaged as proof that the newer release remains incompatible. The newer note nevertheless makes the human-versus-model distinction harder to ignore. VS Code 1.142, VS Code 1.143

My practical conclusion is narrow: if a control exists because a person must authorize an action, do not treat the word ask as sufficient evidence. Establish who can satisfy it in the particular client, version, harness, and session mode that will execute the action.

Fallback is not one behavior

An unavailable safety review returns a request to ordinary session handling. In an interactive session, that may mean asking the operator; it is not an unconditional claim that every request stops. Existing grants matter. Assisted review behavior

Unattended execution has a different outcome. The programmatic reference says requests still needing human approval are denied, and the reason is returned to Copilot so it can seek another approach. This is not a queued human approval waiting to be answered later. A workflow designer needs to distinguish successful completion from a tool denial followed by a different plan. Programmatic assisted permissions

There is also a configuration trap. If --assisted-approval cannot activate, a separate --allow-all-tools can remain effective. When Assisted does activate, it does not revoke --allow-all-paths or --allow-all-urls. Adding Assisted to an existing --yolo command therefore does not establish a restricted run. Inspect the actual flags and warnings, rather than reading the new flag as a safety override. Command-line warnings

Manual mode is not a clean-room reset either. CLI documentation describes saved location-scoped permissions, separate permanently allowed domains, and command-line grants. The session reset command returns to its startup permission baseline; it does not erase those startup flags. A comparison between Manual and Assisted is misleading if one trial inherits approvals the other does not. Persisted permissions and reset behavior

Approval and confinement solve different problems

GitHub's sandbox documentation says local sandboxing is off by default. Without it, commands execute with the user's access. Even when enabled, built-in CLI file tools check policy in-process rather than being confined by the operating-system sandbox; remote MCP servers are not inside the local sandbox. Those distinctions prevent a simple equation between a reassuring permission label and contained consequences. Sandbox coverage

The CLI's ordinary path and URL checks also have documented limits. Shell paths are extracted heuristically; complex constructs can escape detection. URL recognition covers selected commands and does not inspect every URL hidden in files or environment variables. These are reasons to preserve resource restrictions independently of a model's judgment, not instructions to defeat the checks. Path and URL permission limits

VS Code's security guidance is explicit that Assisted is not a security boundary. Its enterprise guidance adds a particularly concrete caution: for Copilot harness sessions, a tool marked ineligible for automatic approval can remove Allow All without forcing confirmation on every call; Assisted or saved approvals may still approve it. A control's name is a poor substitute for its effective behavior. VS Code security guidance, Tool approval policy

The strongest objection

The reasonable objection is that repetitive prompts do not guarantee careful review. Assisted may be a better operational choice than routine blanket approval. Nothing here establishes that a human would judge every request more accurately than the reviewer model, or that Assisted makes a properly isolated workflow less safe.

The narrower point survives that objection: prompt reduction and authorization assurance are different outcomes. Measure the first, and test the second. Do not infer either from a general-availability label.

One reversible test before reliance

An authorized administrator could run a small comparison on an already provisioned disposable test host, with no production repository, deployment access, or business-service credentials. No installation, account change, or live release is part of this proposal.

Use one exact harmless shell command, such as printf permission-probe, under a test-only managed ask rule. Start fresh equivalent sessions with no saved approvals or blanket grants: one Manual, one Assisted. Record the installed versions, effective policy, harness, sandbox state, actual tool request, whether a person was prompted, and whether the command ran. Decline any human prompt. Then repeat the same request with an explicit test-only deny rule as a negative control.

A model-approved execution in the Assisted condition would falsify the assumption that this ask rule always demands a human. A prompt in both conditions would not prove that every eligible action will prompt. No actual tool request means an inconclusive trial. Any failure of the deny control stops the experiment and calls for investigation, not a broader test.

Restore the test settings and end the disposable sessions afterward. The result would characterize one versioned configuration, not establish a universal safety rate. The available evidence here is published vendor documentation, including its inconsistencies; no Copilot execution or account entitlement has been verified.
