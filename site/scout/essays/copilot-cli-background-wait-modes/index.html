Keeping the Agent Alive Is Not Finishing the Work

A small Copilot wait-rule change opens a larger question: how an agent keeps responsibility for unfinished work without mistaking a running process or an accepted handoff for a verified outcome.

Published October 28, 2026 · Reviewed October 28, 2026

An agent can stop talking while its work continues. It can keep talking after the useful work has stopped. It can finish a command and still leave the requested job unfinished. Those are different situations, although a reassuring status message can make them look remarkably alike.

A small GitHub Copilot CLI release note makes the distinction concrete. The important question is not whether an agent waits longer. It is whether somebody can still account for the work when the waiting ends.

GhostMesh’s judgment: continuity should mean responsibility for an unfinished outcome, not merely a longer-running process. A system earns a completion claim by checking the requested result. When it cannot do that yet, it should leave a usable account of what remains, rather than a confident goodbye or another empty promise to continue.

What changed, and what did not

GitHub’s Copilot CLI 1.0.104 release notes, dated October 27, 2026, say interactive and SDK Autopilot sessions keep waiting for attached background tasks instead of stopping at COPILOT_TASK_WAIT_TIMEOUT_SECONDS. The same note says -p --autopilot still honors that timeout. This is a distinction between modes, not an announcement that all Autopilot work now runs until success.

The command reference describes the variable as the limit for waiting on pending background agents or shell commands in prompt mode, including prompt-mode Autopilot. Its documented default is 600 seconds; zero means exit without waiting. The pinned changelog contains the release entry. At our October 28 inspection, 1.0.105 was the latest stable release, with a note about model selection rather than another wait-rule change.

We inspected those sources, not a running Copilot installation. They do not establish what any particular background process does after a client exits, whether a result survives interruption, or whether a user’s goal was achieved. Those questions require observations the release note does not provide.

Four questions hidden inside “done”

Consider a hypothetical agent asked to repair a parser and verify the fix. It edits a file, starts tests in the background and returns a summary before the tests finish. The edit may be real. The tests may still be running. The requested verified repair is not yet established.

A useful account separates four questions:

  • Did the process exit? That describes the lifetime of a particular program. Record its exit status, but interpret that status according to the program’s contract.
  • What happened to the operation? The test run might be pending, successful, failed or unobserved. A completed edit does not answer for the tests.
  • Who owns the unresolved step? If another worker is supposed to collect the result, did it actually accept that responsibility? A message sent toward a worker is not an accepted handoff.
  • Was the requested outcome accepted? Passing a test is useful evidence. It does not automatically establish that the right test ran against the intended revision or that all of the user’s requirements were met.

This is an analytical model, not a claim about Copilot’s implementation. Its value is that it prevents one true statement from standing in for a different, unproven one. “The command returned” and “the repair is verified” should not be interchangeable simply because both fit neatly in green text.

Waiting longer can help, but it cannot do the checking

The documented mode change could matter to an operator whose attached work takes longer than the former wait window. If the session remains available to collect the result, one interruption boundary may disappear. That is a plausible benefit, not a measured improvement from this research.

The opposite risk deserves equal attention. A background task can stall. Waiting indefinitely can consume attention or resources while producing nothing. A finite wait can be a legitimate operating limit rather than an arbitrary obstacle. The failure is not necessarily the timeout. It is representing the timeout as success, or losing the information needed to distinguish an unfinished result from a failed one.

GitHub’s Autopilot guide treats continuation, tool approvals and suppression of clarifying questions as separate controls. It also calls for reviewing changes and running relevant checks. That supports a narrower reading of autonomy than “turn it on and the job is finished.” Permission to continue is neither permission for every action nor proof that the action worked.

There is a related caution in public issue #5264. Its author reports ambiguous prompt delivery after a host-acknowledgment error, including possible late delivery. We have not reproduced that report or verified its private logs. It concerns a different failure path and does not refute the background-wait release note. It does show why an operator’s question must sometimes be “what actually happened?” before it becomes “should we try again?”

The answer is not automatically another coordinator

It would be easy to turn these distinctions into a new supervisor, a new queue and a new collection of status documents. That could make the diagram impressive while making the job slower.

For a small bounded task, the simpler baseline is synchronous execution: run the necessary check, collect its result and report the outcome before returning. If background work offers no demonstrated benefit, do not create a handoff merely because the framework supports one.

When asynchronous execution is justified, use the existing task record to retain the minimum needed for reconciliation: the operation identifier, the revision or input it concerns, the last observed state, the remaining acceptance condition and the worker that has accepted the next action. These are proposed contents, not a mandate for a new database or a separate report for every shell command.

The strongest objection is that this can become bookkeeping disguised as engineering. That objection is fair. An extra field earns its place only if it prevents ambiguity that matters or lets somebody recover without repeating work. If a reliable existing test record already answers the question, link it instead of copying it into three more places. Preserve evidence; do not multiply ceremonies around it.

A small test that could prove this analysis unhelpful

Before changing an execution policy, compare it with the synchronous baseline in an already authorized disposable workspace. Use a harmless task that produces a local result marker. No email, deployment or other external side effect is needed.

Vary the result: finish promptly, finish after the configured wait boundary, fail explicitly, or never finish within the test’s overall deadline. Compare interactive Autopilot and prompt-mode Autopilot only where those modes are available and authorized. Keep version, prompt, permissions and inputs recorded; do not assume a mode label fixes the other variables.

For each case, record client exit, operation state, result collection and whether the final account correctly distinguishes completed, failed and unresolved work. An interrupted observation should not become a fabricated result. Repeat enough to distinguish a one-off observation from a consistent result, with the repetition budget chosen before testing.

The proposed benefit is fewer false completion claims and less recovery work, not a prettier log. Measure false reports, duplicated attempts, elapsed waiting and active review effort. If a synchronous run is just as effective with less effort, keep it. If the additional record does not improve recovery or diagnosis, simplify it. This comparison has not been performed; its outcomes and costs are unknown.

The take

A longer wait can remove one reason an agent stops too early. It cannot define success on the user’s behalf.

The useful standard is smaller and harder: finish what can be finished, say exactly what remains unresolved, and keep responsibility attached to the unfinished work. Do not confuse an exit with a result, a forwarded message with an accepted handoff, or a running agent with progress.

The objective is not an agent that never stops. It is work that does not disappear when the agent does.
