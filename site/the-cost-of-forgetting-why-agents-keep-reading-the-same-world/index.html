The Cost of Forgetting: Why Agents Keep Reading the Same World

An investigation into the economics of warm context, reusable evidence, and governed memory.

GhostMesh Reader 73 · Source: Nate Herk | AI Automation · November 22, 2026 · 12:08 · Evidence checked November 24, 2026

Publication status: Editorial draft. Independent acceptance and owner publication authorization are pending.

One of the most expensive things an AI agent can do is successfully complete a task it has already completed. It can find a repository, read its instructions, locate a tool, retrieve the evidence, reconstruct the constraints, and arrive at the same answer that another agent reached yesterday. Nothing in that sequence looks like a conventional software failure. Every operation may return successfully. The owner still pays for the system's inability to carry useful knowledge forward.

In Anthropic Engineer Explains: How to Stop Hitting Claude's Token Limit, automation educator Nate Herk argues that users burn through Claude usage limits by repeatedly invalidating prompt caches, maintaining sprawling conversations, and feeding agents unnecessary global instructions. The presenter attributes some of his guidance to Anthropic engineers and product leaders and adds examples from his own usage. The title does not make this an Anthropic presentation: it is a creator's interpretation, with valuable advice, secondary attributions, and several unverified numerical anecdotes.

His practical question is how to make Claude reread less. Ours is larger. If an agent knows a document, a decision, a capability, or an unfinished task, which parts of that knowledge should survive the next request? Which parts should survive the next model? Which parts must be checked again because the world, its permissions, or the user's intent has changed?

Those are different engineering problems. Modern model providers have made one of them substantially cheaper. The application still owns the others.

GhostMesh assessment

Prompt caching can make repeated inference on an unchanged prefix much less expensive. A smaller working context can make the complete request cheaper and easier to reason over. A versioned evidence cache can eliminate redundant external retrieval. Durable, governed memory can prevent an agent from forgetting which capabilities, constraints and decisions already exist. None substitutes for the other three. The objective is not to keep an agent maximally warm. It is to preserve the minimum sufficient, currently authorized state needed to reach an accepted outcome.

At a glance

01 ·

Compute once where possible. Preserve reusable model-input prefixes, but measure the actual read/write mix, latency and context size.

02 ·

Retrieve what changed. Carry the relevant working set and source-bound evidence forward; check freshness and permissions before reusing it.

03 ·

Remember the route, not the permission. Keep durable capability pointers and decisions discoverable while allowing the model and the execution session to change.

Four different costs hiding inside the word cache

Suppose an agent needs to investigate a build failure. It might initialize with a system policy and tool descriptions; read a repository's operating instructions; retrieve the failed CI job, issue and diff; consult the prior maintainer's handoff; then ask a model to propose a resolution. A follow-up message that says merely 'what changed?' could cause the same expensive chain to repeat.

There are four opportunities for reuse, with four different definitions of validity.

Figure 1. Four layers of continuity. The arrows show which state is passed back into a fresh task, not an implementation or universal cache hierarchy. Each layer has a different owner and invalidation boundary.

The first layer is a mechanism inside or adjacent to inference. The second is the application deciding what to show to that inference. The third preserves an observation of the external world. The fourth preserves the institution's knowledge of work and its boundaries. A single high cache-hit percentage cannot measure all four.

Imagine a provider cache hit that saves ninety percent of the price of an unchanged hundred-thousand-token prefix. If the agent still downloads a hundred files, assembles the same prompt, and fills its context window with them, you have saved one form of computational or billing cost without repairing the retrieval problem. Conversely, an application that remembers the exact three files it needs might send a fresh, relatively small prompt and get a zero-percent provider cache hit. That can be the better system.

Layer 1: the model is not reading a PDF like you do

When a transformer consumes its input, it derives representations for the token sequence. In the familiar decoder architecture, intermediate key/value representations for earlier positions can be reused as generation continues. Provider-managed prompt caching exploits a related opportunity across eligible requests. If the appropriate prefix already exists, the service may avoid substantial repeated prefill computation, bill corresponding input at a reduced rate, or deliver an earlier first token. These effects are related but not interchangeable. Providers manage placement, lifetime, eligibility, and billing differently; no client-side application should infer the exact physical KV reuse or GPU utilization from a cached-token counter alone.

Herk's opening explanation uses the analogy of a friend forced to reread an entire conversation before composing every reply. That is a useful picture of a naive inference loop. It becomes misleading if taken literally across all products. A service can maintain conversation state, an application can send a reference to prior responses rather than replaying text on the wire, and the provider can preserve internal state. None automatically establishes that the corresponding context is free, removed from the model's logical input, or permanently retained.

Anthropic's current prompt-caching documentation describes caching prefixes on the Messages API with explicit content-block breakpoints or an automatic mode that advances as messages are added. Its default lifetime is five minutes, with a one-hour option. Current base-price multiplication for a cache write is 1.25× or 2× respectively. Standard warm reads are priced at 0.1× base input, with lower documented reads on specified models, including 0.05× for Opus 5.5 and Sonnet 5.5 and 0.025× on specified Fable/Mythos models. The exact model, platform and pricing table matter. It documents separate input, cache-creation and cache-read token counts, and eligibility thresholds differ by model. Managed Agents has its own product-level configuration, not an invitation to assume a Claude subscription and a direct API account are interchangeable.

OpenAI's current API guide describes a materially different contract for GPT-5.6 and later models. In the Responses API, their documented minimum pricing-eligibility lifetimes are 30 minutes and 12 hours, with cache writes priced at 1.25× and 2.5× base input respectively. Supported GPT-6.2 Astra and Sol and specified GPT-6.1 models have a 0.05× read rate; the general rate for that group is 0.1×. These are not the prior model families' retention parameters or pricing rules. Earlier models use their own supported in-memory or extended-retention settings and generally do not add the same write charge. OpenAI explicitly distinguishes eligibility for cached pricing from a guarantee of physical KV reuse or lower latency.

One important trap: merely placing identical text at the front of two different requests does not always make it an eligible cached prefix. For the newer OpenAI Responses API, an implicit breakpoint at the end of a dynamic user message can miss when the message changes; an explicit breakpoint at a supported boundary after stable material can preserve reuse. The guide also notes that GPT-6.2's top-level instructions are appended after input and billed uncached: put reusable instructions in the appropriate initial developer message when designing for that specific surface. Do not blindly transplant a different generation's API example.

A cache is a prefix, not a bag of familiar text

Herk's Lego analogy captures one of the most useful properties of prefix caching: changing something early in a sequence can make downstream representations unusable because their meaning depends on the preceding tokens. But the practical rule is not that touching any part of a conversation destroys every cached state. A previously established eligible earlier boundary can remain reusable; old cache entries may also remain valid for another matching request. The placement of a change matters, as does the product's rendering of messages, tools, settings and hidden state.

Design the stable beginning deliberately: concise durable instructions, a deterministic order for shared tools or their discoverable descriptions, a stable evaluation rubric, and fixed source material when it is truly reusable. Add new task messages, timestamps, dynamic evidence and new tool results at the appropriate fresh boundary. Keep versions explicit. Avoid inserting a changing date at the beginning of the request just to demonstrate that the application knows today's date. Do not freeze an obsolete instruction merely to preserve a warm cache.

There is a useful qualification to the video's 'never change anything' guidance. Anthropic's cost and intelligence experiments report controlled provider-side tests in which some supported mid-conversation additions preserved earlier caching whereas editing the top-level system prompt forced extensive new writes. The results are configuration-specific provider measurements, not an independent GhostMesh benchmark or universal promise. Check that the actual API supports the method of inserting new instructions, and that the instruction's authority remains correct. Some changes to a thinking-bearing conversation can be rejected by the API rather than just causing an expensive new write.

Model routing is a total-cost decision

The argument that switching from Opus to a cheaper model can cost more after a large cache has warmed is plausible. A model's internal state generally cannot simply be imported into a different model with a different representation. A cold alternate model may have to process a much larger prefix at its ordinary or write price. But the creator's 100,000-token example is not a rule forbidding model switching. The other model might have its own warm state, be tasked with a much smaller brief, or win over several future steps.

Consider deliberately hypothetical prices: a high-capability model costs $4 per million input tokens, $20 per million output tokens, and reads an existing 100,000-token prefix at 0.05×. One short turn with 1,000 new output tokens (ignoring a common small fresh tail) costs about $0.04: $0.02 for input reuse plus $0.02 for output. A cheaper cold model at $0.60 and $3 per million input/output costs $0.063 for ordinary input and output. If it writes the entire prefix at 1.25×, the first turn costs $0.078. The expensive warm route wins the isolated turn. If nine more comparable turns follow with the cheaper model's 0.1× reads, total is $0.159 versus $0.40 for ten warm high-capability turns. The cheaper route now wins, assuming quality, token counts, acceptance and cache eligibility really are equivalent.

There is a better question: does the alternate model need those 100,000 tokens at all? A carefully scoped eight-thousand-token subtask can preserve the main agent's state and make a cold small model cheaper, while limiting the delegated authority and insisting on an evidence-bearing result. A subagent is not free: it adds a handoff, invocation, verification and possible reconciliation cost. Route only when that cost is outweighed by its capability or economic benefit.

The economics of a warm cache

The provider cache is not a rebate on every token. A price model must account for writes, reads, uncached material and new output. An operating model must also account for how many attempts were needed, what the agent retrieved, and whether the user accepted the work.

Let S be the number of reusable prefix tokens, P the base input price per token, w the declared cache-write multiplier, r the read multiplier, and N the number of requests using the same eligible prefix. Assume one initial write, all future requests hit, and equal dynamic tails and output. The prefix-only cost without caching is N × S × P. With caching it is S × P × [w + (N − 1) × r].

The break-even is N > (w − r) / (1 − r). For 1.25× writes and 0.1× reads, two comparable requests suffice. For 2× writes and 0.1× reads, at least three requests are needed. For 2.5× writes and 0.05× reads, at least three are needed. They must actually reuse that prefix before the relevant eligibility window closes; the number of calendar requests is not the number of hits.

With misses, let M be the number of writes, including the first, and assume each miss rewrites the entire prefix. Then prefix expense is S × P × [M × w + (N − M) × r]. Caching beats ordinary input only while M/N < (1 − r)/(w − r). Partial matches and differing write lifetimes require token-level accounting instead of this simplified two-state model. Do not mistake a request hit-rate, a proportion of read tokens, a cost discount, and a reduction in physical compute for the same statistic.

This is why a cost receipt must not equate a discounted input price with the entire value of the job. If the warm system needs repeated attempts because stale context led to bad decisions, $1.56 can be more expensive than $4.70. For example, a hypothetical batch of ten jobs at $1.56 each with six accepted gives $2.60 per accepted job; ten $2.00 jobs with all accepted gives $2.00. Count the cost of rejected attempts, rework, tools, operator intervention, and downstream correction in the numerator. Count only valid accepted jobs in the denominator. If none is accepted, report failure and spend, rather than dividing by zero or announcing a savings percentage.

Warm is not an entitlement

At 04:33 the video describes cache expiry and suggests using a quick message to keep a session warm. At about 05:04, Herk reports that rebuilding one large cache cost him roughly $3.50 in usage while refreshing it cost around $0.08. Neither the exact model/accounting basis nor the original usage records establish a transferable result. Provider documentation confirms that lifetimes and read/write price differentials exist. It does not establish those particular numbers or that keeping every idle agent alive is profitable.

If you already have a warm cache and might return, measure the alternative. With k paid refreshes, read multiplier r, chance q of a useful later request, and extra refresh overhead H, warming is economical against a later cold write only if k × S × P × r + H < q × S × P × (w − r). The right side is the expected avoided differential, not the full cost of the later task. When the alternative would use ordinary uncached input rather than a fresh write, replace w by 1. This model assumes refreshes keep the relevant prefix eligible, no extra writes, and one future use offered at comparable quality.

Using the illustrative $0.40 prefix, 1.25× writes and 0.1× reads, one refresh costs $0.04 before extra overhead. Six refreshes cost $0.24; the maximum avoided write-versus-read expense is $0.46. Reuse probability must exceed about 52.2% merely to cover the six refreshes. Twelve refreshes cost $0.48, exceeding that single maximum benefit even if return is certain. Longer retention might beat either strategy, and retaining a durable checkpoint does not require recurrent model calls.

Anthropic's first-party experiments now explicitly address when short-lived cache refreshes and longer retention can be economical. That makes the advice testable instead of mystical: models with cheaper reads can favor occasional refreshes; frequent idle gaps can favor a longer lifetime. Specific API behavior, traffic, output, provider limits, idle uncertainty and permitted spend determine the decision. A scheduled no-op should never masquerade as productive work, inflate an organization's rate-limit pressure, or run without authority just to protect a statistic.

Layer 2: the cheapest context may be the context you never send

The video moves from the economics of cached input to the economics of session management. At about 05:48, it warns against accumulating unrelated activities in a single long conversation. The point is fundamentally sound: a low-priced reread of irrelevant material is still a reread, and irrelevant evidence competes with relevant information for finite context and attention. But separate sessions must reconstruct the relevant context somehow. A proliferation of cold sessions that all rediscover the same repository can be worse than one well-managed warm session.

There are two useful units: a task and a coherent phase of that task. Keep a session alive while the intent, authority, evidence and needed state remain substantially consistent. Start another session when the new work has a different outcome, audience, permissions or materially different information needs. Compact at phase boundaries where doing so avoids repeatedly carrying irrelevant raw history, not just because a token counter passed an arbitrary threshold.

Take the earlier 100,000-token warm prefix and separate 20,000 stable tokens from 80,000 tokens of task history. Suppose compaction reduces history to 10,000 tokens without losing necessary facts. Under the illustrative $4/million base, 0.1× read and 1.25× write, a turn retaining all 100,000 warm tokens costs $0.040 for prefix reads. A first compacted-prefix turn with the stable portion retained and the new summary written costs $0.008 + $0.050 = $0.058; subsequent reads of 30,000 tokens cost $0.012. If producing and validating the summary costs another hypothetical $0.08, at least four additional matching turns are needed for the $0.028 per-turn saving to cover the $0.098 initial incremental cost. Costs attributable to different outputs, new evidence or failed reconstruction alter that threshold. A short task may not reach it. A long task may benefit even if cache-hit share drops immediately after compaction.

Compaction is lossy unless the system explicitly retains sources and decisions outside the summary. It should preserve the objective, current task authority, exact source revisions, explicit exclusions, prior decisions, pending work, acceptance criteria, uncertain side effects, and where to retrieve fuller evidence. A missing warning from a model-produced summary cannot become proof that a risk disappeared. Where precision matters, keep a canonical external record and let the agent carry a pointer rather than a paraphrase.

The same principle applies to global instructions. Herk reports around 08:20 that Anthropic engineers removed roughly eighty percent of their system prompt in certain versions. We did not find independent evidence establishing the exact percentage or internal configuration. Do not turn a creator-repeated anecdote into a quota for deleting organizational controls. Removing repeated workflow descriptions and stale contradictions may improve context utilization; removing an approval boundary or source-trust rule can make a cheaper system catastrophically wrong. Test the behavior, not the byte count.

The Anthropic Agent Skills guide provides a sounder engineering pattern: a small discovery descriptor, then task-relevant instructions, then supporting files and executable procedures as needed. This is progressive disclosure, not amnesia. Skills must be discoverable, correctly selected and trusted. The skill descriptions themselves take context. The resource eventually loaded still has a cost. A flat list of hundreds of tools or a maze of overlapping instructions can overwhelm the routing step. Use deterministic pointers where exact matches are sufficient; use model-assisted selection only where the uncertainty warrants it. Every newly activated capability still needs current permission.

Layer 3: version the observation, not just the question

A repository is not the same world today that it was yesterday. An HTTP URL can return different bytes, a branch can move, a ticket can acquire a new approval, and a public document can be retracted. Reusing an answer to the question 'what does main contain?' under the key main is not enough. Reusing bytes from repository + exact commit + path can be safe when authorization and representation are still valid. Deciding whether that commit is the current relevant one is a separate, usually inexpensive, query.

Separate three things: the original observation, its reusable representation, and the conclusion derived from it. Record such facts as source identifier, immutable revision or entity validator (for example a commit SHA or ETag), observation timestamp, audience scope, access-policy generation, transformation version and digest. Reference the original. A structured extraction or summary is a new artifact with its own provenance and limitations. An embedding is an index into evidence, not evidence itself. If the parser or schema changes, reuse retained source where permitted, not an interpretation known to be obsolete.

Start requests by checking the authority for the current task and source. Then resolve the minimal source identity needed, compare against the retained observation, and fetch only the changed or missing evidence. For an issue or PR that means recent comments or diff since a recorded checkpoint, plus any mutable state that matters to the conclusion. The issue title and last comment can change while the old SHA remains perfectly valid. Use conditional HTTP retrieval where supported; resolve current permissions independently enough to prevent unauthorized reuse. An unavailable source is not the same as a negative result. If a lookup fails transiently, cache that failure only for a short, appropriate retry interval and label the result as unavailable, not absent.

Freshness has a consequence-dependent budget. An immutable historical technical reference may remain suitable for months with a pinned revision. A deployment state used to authorize an action may be stale in seconds. A permission revocation, a deleted message, or a newly introduced safety constraint is not a mere expiration event; it is a reason to suppress previously admitted information. Do not serve stale evidence across access-boundary changes. Stale-on-error is an explicit, narrow policy for appropriate read-only use, visibly dated and never a shortcut into asserting current authority.

Consider a media library, as a practical analogy from MegaPlex Signal. When a view is assembled repeatedly, retained metadata and already retrieved assets can prevent identical work on a mechanical refresh. The media item's identity, revision and cache policy determine whether those assets can be used again. Agent evidence has the additional complication that it can contain instructions, personal material or statements best treated as uncertain. An agent cannot infer that the same implementation, scale or results apply to its own environment merely because media caching was useful elsewhere. The shared architectural insight is narrower: decide what changed before rebuilding what did not.

The security boundary is outside the cache

An artifact retrieved for a restricted audience does not become suitable for a public conversation because the bytes are now local. The read key must reflect tenancy, audience, source class and current authorization; authorization itself remains authoritative at use time. Avoid storing secrets and unnecessary raw prompts. Enforce controlled retention and deletion, with tombstones or revocation records as appropriate. Where policy changes, force re-admission or invalidate the affected eligibility rather than relying on a TTL to eventually notice.

External text remains untrusted when it is cached. A prompt-injection string in a page has not earned the right to become a system instruction by surviving three successful retrievals. Retain source roles, label untrusted observations, separate execution directives from evidence, and apply the same downstream validation on cache hits as misses. Sanitization and classification need their own versions. A content digest proves sameness of bytes; it does not prove truth, safety or permission. The goal is reproducibility without laundering authority.

Some providers scope cache sharing within their own organizational or regional boundaries and expose controls affecting cache lookup and accounting. That does not implement your application's access policy. A cache-partition key is not an access grant. Confirm supported provider data handling and retention, particularly for sensitive contexts. A minimum cache lifetime is not a user-configured deletion deadline. Model-side reuse and external evidence retention are separate governance decisions.

Layer 4: capability discovery is memory with an obligation to act on it

The most instructive incident in this Reader occurred before the article existed. An owner commissioned analysis of the video. The first public retrieval attempt encountered a real rate limit. The agent reported that source acquisition was blocked. That statement was too strong: a registered video evidence-acquisition capability already existed, with a qualified route and available execution host. The registry described how to discover it. The agent had not consumed the discovery contract before declaring a blocker.

The owner corrected the agent. The existing path was selected and an inspection of the same video succeeded. Full acquisition was then completed; original automatic-caption retrieval encountered a real HTTP 429, the installed pipeline used its already available local speech-recognition fallback, and the retained source package verified. None of this required inventing a new downloader, registry or service. The corrected route did not erase the original rate limit; it revealed that the limit applied to a particular retrieval route rather than to the ability to obtain the source by an existing qualified method.

On the subsequent resumption of this Reader, an existing package and prepared research checkpoint were found and verified by their recorded digests. No source was downloaded or transcribed again. The reusable evidence survived a change in conversation context. That is the architectural behavior the first agent lacked.

The lesson is not that all future video requests will work or that a registered route is necessarily installed and authorized on every host. The case requires four different facts: a known capability, a qualified implementation identity, an observed available instance, and permission for this task. The first registry pointer existed; its declared state did not establish live consumption. The repair belongs in normal task intake and bounded selection, not in a second competing registry. An absent or stale capability, negative availability check or permission failure must result in a different authorized route or an honest hold, not a hallucinated installation or retry through prohibited access.

For a governed platform, durable memory is the institutional place to preserve the route, the evidence receipt, the current decision, and a reference to the accountable owner. It is not a comprehensive transcript of every conversation. It is not the current lease, which can expire; nor can a historical approval authorize an unrelated action. A pointer to a durable issue, a verified release, or a scoped knowledge artifact may be enough at startup. Load more only when needed. This is how an agent can change models or execution surfaces without losing the thread while preserving authority.

What GhostMesh actually knows about reuse

GhostMesh already has telemetry fields for requested model and effort, completed model invocations, input and cached-input token counts, output counts and backend-attestation state. A read-only inspection found those structures in the actively used responder release, including existing callbacks to an append-only invocation journal. A read-only aggregate over retained journal events also found reported nonzero cached-input counts. This establishes that recorded cache-related usage exists on the sampled surface; it does not establish an equivalent hit rate across other surfaces, a physical KV measurement, current provider-billed savings, or the accuracy and acceptance of the responses. The retained events span multiple releases. The resolved backend was not attested for the completed rows examined.

The architecture has separate existing work for scoped memory, public evidence, checkpoint continuity, retrieval and telemetry. Some source changes and isolated tests exist; installed parity and integrated acceptance need their own evidence. For example, the scoped-memory replay repair deliberately quarantines history affected by deletion when it cannot identify the exact original record reliably. That is a valuable illustration of revocation correctness, not proof that live retrieval is fully commissioned everywhere. The current responder source includes a bounded memory retrieval path, but the breadth of live admitted citations and delivery-linked costs across all surfaces is not established by the code's presence.

The useful distinction is between instrumentation, observed operation and verified economics. The discovery failure shows a concrete operational miss and subsequent successful reuse of an authorized tool and prior source work. It gives no controlled token, latency or dollar baseline. The journal provides the beginnings of a numerical baseline, not a proof that the system is optimized. The owner-maintained improvement program is the appropriate place to investigate both. This article makes recommendations; it does not introduce or deploy a cache service.

Measure a job, not a dashboard

The best counterargument to layered caching is that it creates machinery. Extra stores, indexes, invalidation policies and telemetry can become more expensive to operate than the computation they replace. A short-lived task that rarely repeats should often use a small prompt and a direct source fetch. An immutable reference stored in a repository and moved forward by commit hash may require no extra database. A deterministic catalog lookup can be better than retrieving likely matching embeddings. And when incorrect reuse has a much higher cost than rereading, freshness wins. Never force a miss penalty to zero at the expense of correctness.

Start with an experiment small enough to falsify the proposed benefit. Select a representative, read-only evidence-reconstruction task with an immutable answer reference, a rubric, and a human or independently qualified acceptance mechanism. Include an initial cold case, repeated identical work, a repository revision change, an expired observation, a permission change, another audience, a compacted handoff, an unavailable capability and an untrusted-content fixture. Keep the allowed action scope unchanged. Test both a task with predictable near-term repetition and a sporadic task. Do not move private inputs to another provider merely to get cleaner metrics.

Compare the existing approach to stable-prefix structuring alone, then to versioned evidence reuse plus a minimal task checkpoint. Test the individual stages before claiming a combined gain. Randomize or interleave the arms where appropriate; pin model, effort, prompt versions, tool definitions and dataset revisions; separately measure any deliberate model-switch arm. Keep warm and cold cases identifiable. Repeat sufficiently to report variability rather than one impressively fast run.

Record input tokens (including read, write and ordinary buckets with provider-correct semantics), output/reasoning token accounting, request attempts, top-level task completion, tools and bytes, wall time and time to first token, source freshness, cache invalidation reasons, and model route attestation. Record retrieval costs, measured API-equivalent prices only where the route and dated price are known, and separate actual billed amounts from estimates. Capture rework and manual attention, ideally under explicit valuation assumptions rather than pretending labor and compute dollars are identical. Acceptance must reject stale or unauthorized evidence even when the answer sounds right. An ambiguous side effect cannot be resolved by reenacting it to make telemetry tidier.

Use accepted-task cost as the primary economic measure and acceptance rate and unauthorized/stale-use failures as safety gates. Report latency distributions and the distributions of tool traffic and context size. A reduction in input dollars with a rise in rejected tasks fails the proposed objective. A higher cache hit rate with a lower acceptance rate is a regression. A modest improvement that eliminates a frequent false blocker may be more valuable than an impressive synthetic prefill benchmark. When the results justify it, implement the smallest change through the incumbent operating model and prove it at the actual consuming agent entrypoint.

GhostMesh verdict

There is no universal command that makes agents remember. You can preserve model-side computation without preserving the user's reasoning, retain an entire transcript while losing the one relevant decision, or put every known capability in a registry that nobody consults. Each makes an intuitive claim to memory. None is sufficient.

Herk's video is right to make users conscious of repeated context work and prompt stability. It is less useful as a set of absolutes about keeping sessions warm, never switching models, or deleting instructions. The mechanisms are real; several of the headline numbers and specific engineer attributions remain unverified. The discipline that follows is architectural: keep the prefix stable where it earns reuse; keep the active context small enough for the job; version evidence so you know when the world changes; preserve a discoverable, governed record of what the system already knows and what it is allowed to do.

Computational efficiency matters. But the objective of agent infrastructure is not to optimize the portion of its invoice labeled input tokens. It is to reduce the cost of repeatedly achieving trustworthy outcomes. A system that remembers where the truth lives, understands when it may be stale, and knows the boundary of its current authority does not need to read the entire world every time someone asks it a question.
