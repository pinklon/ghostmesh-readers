The Page Is Part of the Proof

Thariq Shihipar makes a persuasive case for asking Claude Code to create HTML instead of another long Markdown file. A page can make an argument easier to see, compare and challenge. It can also make a weak argument look finished. The useful question is which form helps a human inspect the work and its evidence.

Using Claude Code: The unreasonable effectiveness of HTML ↗, by Thariq Shihipar, published May 20, 2026. Shihipar describes how he and others on the Claude Code team use HTML for visual explanations, specifications, code review and purpose-built editing interfaces.

This Reader tests the argument and its limits. The author explicitly credits Markdown's simplicity, portability and editability, and describes his own preference as unusually HTML-maximalist. The essay is a practitioner account, not a controlled study of comprehension or productivity.

Source boundary

The original page and linked examples are public. A private exact-page capture supports this reading, but its full HTML is not republished here. Standards and security documentation establish format capabilities and design duties; they do not measure this team's outcomes.

01 / The genuine problem

A document can be easy to generate and hard to examine.

In the opening of his essay, Shihipar says that long Markdown plans become hard for him to read and harder to get colleagues to read. HTML lets Claude organize a specification with visual hierarchy, tabs, diagrams, responsive layout and links. The examples include a comparative approach grid, an annotated code review and a custom editor that exports a prompt or a diff. His claim is strongest where a reader must compare alternatives or manipulate a parameter, because linear prose makes those tasks laborious.

That is a meaningful diagnosis of a review bottleneck. A team can have a complete text record that nobody actually inspects. Yet the essay offers examples and personal experience, not a randomized comparison or a measured error rate. An attractive page could increase attention, or simply increase confidence. GhostMesh should distinguish the observable affordance from the unmeasured outcome: HTML can arrange a comparison; this source does not show that the arrangement caused better decisions.

Presentation is part of an evidence path. It is not evidence that the presented conclusion is right.

02 / What the page can do

The advantage is a richer review surface, not a different file extension.

HTML can combine text, tables, SVG, CSS, images and controls in one browser document. Shihipar's examples use that range for visual exploration, code understanding and small editing interfaces. A side-by-side design comparison makes tradeoffs simultaneously visible. A slider can expose how a change affects an interface. An export button can return a precise parameter choice to the code workflow. These are valuable affordances when the reviewer needs to see a state, not just read its description.

But the interface must preserve the information under the visual arrangement. W3C accessibility guidance asks that structure and relationships conveyed visually can also be determined programmatically or found in text. A chart without its underlying values, a tab whose hidden panel cannot be reached by keyboard, or color as the only signal can make a polished page less reviewable for some readers. HTML permits semantic structure; generating HTML does not guarantee it.

The same distinction applies to sharing. A browser link is convenient once a document is hosted, but a link introduces hosting, access, retention and revision questions. Which version did the reviewer see? Can a later deploy silently alter it? Are its images and scripts local or requested from other hosts? The page needs a stable artifact identity if its appearance helps authorize a consequential decision.

03 / The false format war

Markdown can remain the record while HTML becomes the lens.

Shihipar acknowledges Markdown's low-friction editing and portability, then says that he now asks Claude to make HTML for many tasks. That describes a change in who performs edits and what the human reviews. It does not prove that a plain-text source has lost its value. The CommonMark specification describes Markdown as structured plain text that can be converted to HTML. A team can keep a diffable text or data source, generate a richer page for review, and retain both with the same version identifier. HTML can also be authored directly when the interaction itself is the work. The choice follows the artifact's job.

A direct HTML file may be the better source for a prototype, because layout and behavior are substantive. A short decision memo can remain plain text because it is easy to edit, quote and review in a diff. A complex report might use structured data, prose and a generated HTML view. These are not universal format rankings. They are different ways to expose what changed and what the reader must decide.

The strongest argument against a cautious dual-record approach is operational simplicity. If maintaining separate source and rendered files causes drift, the richer page may be the only version anyone reads. Shihipar's point about actual engagement matters: a pristine Markdown file that sits unread is a poor review system. The answer is to generate and check the page from a pinned source where feasible, or to treat the HTML itself as the reviewed source with an inspectable diff and versioned dependencies.

04 / The trust boundary

A document with behavior needs document-level controls.

Shihipar's custom editors are appealing because they can turn a change of mind into an exportable prompt or diff. They also cross a boundary that a simple text file usually does not. HTML may contain scripts, embedded resources, forms and links. What can the file read, send or replace when a reviewer opens it? Content Security Policy documentation describes controls that restrict where a page may load scripts and other resources; the existence of those controls is a reminder that browser content has execution and network capabilities. This is a general property of the medium, not a claim that Shihipar's examples are unsafe.

For a review artifact, the minimal design is often a static file with no remote dependencies. If interaction is necessary, pin its script and data, restrict network access, inspect any import and export path, and disclose what clicking a control will do. A code-review visualization should link each annotation to the exact diff and commit. A report should preserve the underlying values behind charts. A generated editor should export a narrow change rather than silently write to a repository. These are proposed GhostMesh controls, not results demonstrated in the essay.

There is a privacy question too. The essay notes that Claude Code can draw on local files, MCPs, browser state and Git history. That input reach helps produce richer explanations, but any artifact intended for sharing needs a deliberate review of source snippets, personal data and internal links before upload. A convenient browser URL should never be mistaken for proof that the material behind it was meant to be public.

05 / A practical choice

Pick the smallest surface that reveals the decision.

GhostMesh would choose by review task. If the job is to approve a few paragraphs or inspect a small code change, plain text and its diff may be enough. If the job is to compare six interface directions or explore a parameter's consequences, HTML can make simultaneous inspection possible. If the job is to approve a technical claim, either format still needs links to source material, visible assumptions and an account of what would falsify it.

Short decision or code changeText plus exact diffPresentation work hiding a small disputed choice
Visual alternativesHTML comparison with labels and source linksAttractive mockups without comparable criteria
Interactive analysisBounded HTML controls and exportUnpinned data, scripts or invisible state changes
Shareable researchVersioned page plus source and limitationsA polished conclusion with no inspectable evidence

This is a proposed operating rule, not an empirical result. The original essay establishes credible use cases for HTML and makes the human review problem vivid. It does not tell us which format produces fewer wrong approvals across different teams, tasks and accessibility needs.

06 / A test that could change the call

Measure whether the page improves review, not whether it looks finished.

Take a real, non-sensitive specification and prepare two versions with the same facts and deliberate, disclosed test defects. One is a clear Markdown document; the other is an HTML artifact with the comparison and interaction Shihipar recommends. Randomize reviewers and order. Ask them to identify unsupported claims, missing constraints and the best option under a stated rubric. Measure decision accuracy, time, corrections after discussion and whether the final exported change matches the chosen option. Repeat with a short memo and a visual design problem; one format need not win both.

Then inspect the artifact itself. Can a keyboard-only or screen-reader user recover the same relationships? Does it work offline? Are external requests and scripts visible? Can a later reader reproduce the version that was approved and trace every chart or annotation to its source? If HTML improves error detection without weakening these checks, use it more often. If it only increases reported confidence or creates a harder-to-audit artifact, keep the simpler surface or repair the generator. This experiment has not been run by GhostMesh or established by the source essay.

07 / GhostMesh's call

A richer page should make the human more accountable.

Shihipar is right to challenge the assumption that an agent's long Markdown output is automatically readable because it is easy to produce. HTML can turn a plan into a comparison, a code change into an annotated object and a report into something colleagues will actually open. His practical examples are worth trying. The governing question is whether the richer surface lets a reviewer see the claim, the source, the alternative and the consequence more clearly.

The page is part of the proof only when it exposes the path back to evidence and forward to an accountable choice.

That means treating the artifact as a versioned interface to a decision. Keep its source or authored bytes, dependencies, export behavior and accessibility inspectable. Test whether readers catch more important mistakes, not merely whether they prefer the design. HTML and Markdown can both serve that end. Neither file format can supply the judgment on its own.
