Skill count is not context cost

At 01:42 Ondrej separates skill descriptions from full bodies. At 02:09 he warns that even descriptions consume attention at scale. Anthropic documents progressive loading; Codex likewise has bounded discovery. The cost depends on what the harness exposes, not how many files exist.

The useful unit is the discovery surface. A hundred skills stored on disk do not consume a hundred bodies of instructions if only a compact index is shown and the selected skill is opened on demand. Conversely, ten broad descriptions can be costly if they are repeated in every prompt and compete for the same intent. The transcript mixes these mechanisms under one phrase, “too many skills”; an engineering analysis must separate them.

The vendor documentation is narrower than the video’s claim. Anthropic describes metadata-first progressive disclosure. Codex documents a bounded initial skill list, with possible truncation or omission. Neither specification promises that every model, integration or version uses identical discovery rules. An observed token increase should be attributed to the exact harness and configuration before it is attributed to installed count.

The selection problem

At 03:00 the creator criticizes broad descriptions. Ambiguous metadata can make the wrong skill attractive. The correct measure is selection precision and false invocations, not a raw catalog-size limit.

Consider three descriptions that all claim to “review code”: one checks security, another verifies API compatibility and a third checks visual regressions. The model may choose the wrong one even when the total catalog is small. Removing unrelated skills will not fix overlapping descriptions; better names, explicit triggers, exclusions and ownership might.

Selection error is not the same as task failure. A skill might be selected correctly and still execute poorly because its instructions are stale. Another might be invoked unnecessarily but have no material consequence. A useful experiment records the expected skill, actual invocation, output correctness, latency and context cost separately. Without that separation, a benchmark can reward the wrong mechanism.

Rare does not mean useless

At 11:18 and 14:19 he recommends pruning unused skills. That is a sensible inventory prompt, not a universal 80–90% deletion target. Incident recovery, compliance and security skills may be critical precisely because they are rarely needed.

A recovery playbook might be used once in two years. Its value is precisely that it remains available when a production outage or audit finding makes it urgent. A simplistic least-used ranking would delete the most valuable low-frequency procedures first. This is why invocation frequency cannot be a deletion policy by itself.

A safer retirement rule asks whether the skill is duplicated, outdated, unsafe, out of scope or no longer owned. Archive reversible candidates and preserve the ability to restore them. For critical workflows, verify that a named owner, current runbook and authorized execution path remain. No mass removal is warranted by this source.

A skill is not permission

At 29:00 he compares skills to SOPs. Reusable procedures can improve consistency, but a markdown skill cannot authorize privileged actions or replace an approval gate.

The analogy to standard operating procedures is helpful for consistency, but dangerous if stretched. An SOP describes how work should happen; it does not grant a technician access to a regulated system. Similarly, a skill file may explain how to rotate credentials or change a production service, but the agent must still obtain the applicable authorization and respect separation of duties.

For GhostMesh, the execution boundary belongs to the tool, repository protection, identity and owner approval, not to prose embedded in a skill. A malicious or outdated instruction can be retrieved with the same ease as a useful one. Provenance and review are therefore part of skill quality, not optional bureaucracy.

Scope before scale

At 33:40 and 36:56 he discusses portability and global scope. The transferable architecture principle is to expose relevant instructions on the right execution surface and avoid broad global injection.

A globally exposed skill has a larger discovery and trust footprint than a repository-local instruction. But “global” is not automatically wrong: a narrow, well-maintained emergency procedure may need to be discoverable across projects. The meaningful question is whether the metadata is relevant to the current task and whether the body is fetched only when needed.

Cloud portability adds a second constraint. A workflow that works on one workstation may assume local paths, credentials, tools or permissions unavailable in a cloud agent. Portability should be tested against the target surface rather than asserted because both systems can read markdown.

Reuse needs provenance

At 39:00 the creator advocates team-shared skills. Safe reuse also requires ownership, versioning, trust boundaries and review.

Sharing a skilled engineer’s workflow can preserve hard-won operational knowledge. It can also propagate outdated assumptions at machine speed. A team skill should say what problem it solves, who maintains it, what it may change, how to test it and when not to use it.

The creator’s examples are useful demonstrations of personal workflow design, not proof that sharing produces equivalent outcomes for every team. Measure adoption and quality after transfer, not just installation. A trusted source still requires a current review when the environment or privilege boundary changes.
