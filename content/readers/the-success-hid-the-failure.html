The Success Hid the Failure

Agents can finish the job while concealing the broken instructions, wasted tool calls and unnecessary retries that made the work expensive. A green result does not mean the system is healthy.

Ben Holmes · Warp · AI Engineer · November 6, 2026 · 19:19 · Original GhostMesh analysis

Verdict / Worth studying, bounded adoptionWatch for the failure mode and the practical inspection method. Do not treat the score dashboard or merged improvement PRs as controlled proof of better engineering. GhostMesh should use existing execution receipts to fix recurring friction before adding a continuous grading loop.

Three questions before you watch

What is the claim?

Holmes describes agents reviewing prior conversations and tool outputs, assigning quality scores and proposing changes to skills or configuration. The loop can surface defects that a successful completion hides.

What is actually shown?

A vendor presentation walks through rubric scoring, Skill Doctor and improvement proposals. Its examples include agents hunting for test ports because instructions were stale, repeated changelog corrections and a missing subagent configuration. These are useful demonstrations of a mechanism, not independently measured production results.

What should change?

Instrument neither everything nor nothing. Inspect the execution traces GhostMesh already retains, identify a repeated failure with a real cost, correct the source instruction, and compare accepted outcomes and total effort before and after. Keep a person responsible for the change.

A successful agent can hide a broken system

The familiar evaluation asks whether a task finished. That is essential, but incomplete. A persistent agent can recover from a stale command, a bad port, a wrong path or a contradictory skill. If its final answer reports success, operators may never see how much time and money the recovery consumed.

Holmes's port example at 07:52 makes the failure visible: the agent worked around outdated harness guidance by probing its environment. The problem was not primarily insufficient model intelligence. It was a bad local operating instruction.

The strongest idea here is not autonomous self-improvement. It is a different unit of evaluation. A completed task and an efficient, policy-correct execution are separate observations.

The loop he proposes

  • Retain agent conversations, tool requests and tool responses.
  • Grade selected runs against explicit rubrics such as redundant tests, noisy comments and wasted work.
  • Aggregate recurring failures rather than chase every isolated anomaly.
  • Generate a proposed change to the relevant skill, configuration or repository.
  • Review the change and observe subsequent runs for improvement or regression.

That loop is technically coherent. Its value depends on the signal quality of the graders, the cost of collecting evidence and the authority boundary on suggested repairs.

The case against another automated supervisor

More scoring is not automatically better learning. A model grading a model may reward its own writing preferences, penalize appropriate caution or miss expensive but necessary investigation. If the same model family performs the work, judges it and rewrites the instructions, correlated errors can become institutionalized.

Centralizing full transcripts and tool outputs also creates a security and privacy concentration point. Prompts can contain credentials, personal information, proprietary source code and misleading instructions. Retention and access controls matter more than a polished dashboard.

Finally, a daily grading fleet is itself a workload. Without a cost denominator, an apparent token saving on a repaired task can be overwhelmed by constant evaluation, review and maintenance. The correct measure is net useful work accepted per unit of compute and operator attention.

What GhostMesh should borrow

GhostMesh already knows the pattern: agents work around stale commands, duplicate checks, ambiguous ownership and overly elaborate qualification paths. We also already have issue receipts, CI outcomes, runtime traces and explicit operator decisions. Their existence means we can test Holmes's insight without building Warp's entire factory around it.

Start with one recurring failure class. Sample comparable completed runs before and after a narrow instruction correction. Count repeated failed tool calls, elapsed time, total tokens where available, review time and accepted useful outcomes. Keep exceptional cases visible. A genuine improvement reduces friction without lowering correctness or bypassing authority.

If the evidence is weak, stop. If it is strong, revise the existing skill or operating instruction and retain the reason for the change. The system earns another layer of automation only when the first small experiment proves it is needed.
