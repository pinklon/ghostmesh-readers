The Home Repo Is a Map, Not a Monorepo

One versioned starting point for agents across multiple codebases, with the original boundaries intact.

In The Home Repo Pattern: Run agents across ALL your repos, Matt Pocock describes a problem common to multi-repository organizations: coding agents need shared skills, steering files, operating knowledge and tools, but each repository sees only its local setup. Copy everything everywhere and versions drift. Keep shared instructions only in personal home directories and team governance disappears. His proposal is a home repo, a versioned workspace where agents begin their sessions and find pointers to the separate repositories they need.

The idea is deliberately small. Common guidance and tooling live in one place. The storefront, payments API and other codebases retain their own Git histories, issue trackers and build instructions. The agent can navigate or clone them, and use worktrees when multiple tasks overlap. Pocock demonstrates his personal home repository and extends the pattern to a business wiki and integrations with services.

GhostMesh's architectural question is where that shared launch point ends. A home repo can reduce duplicated context and improve discovery, but it must not become an unreviewed grant of authority over every repository and connected system. This is a practitioner demonstration, not measured evidence that it improves completion rates or safety.

One starting directory, multiple repositories

Copies and personal defaults become invisible architecture

At 00:27, Pocock uses a storefront, payments API and dashboard to illustrate the ordinary case. An agent can edit more than one repo, but the shared instructions and skills often get copied into each codebase or installed in a developer's local user directory. Either choice can diverge from what the rest of the team expects.

These are distinct problems. Duplicates create version skew; personal-only instructions lack team review; and a repo-local session may not see the broader dependency. None requires rewriting the deployment process. The design opportunity is a reliable, versioned discovery surface.

A home repository is an entry point, not a code merger

At 02:20, Pocock describes running agents from a single home repo containing skills, steering files, wiki material and tools. Pointers connect that home to other working directories. Those repositories still own their source, branches, releases and issues.

His companion article sharpens the rule: move true shared instructions into the home repo, but keep repo-specific build commands, documentation and agent guidance where they are. It even proposes a read-only inventory and an approved migration plan before any files move. Centralize only what is genuinely shared.

A pointer is useful; it is not an ownership check

At 02:53, Pocock shows an instruction file listing paths to important repositories. An absent repository can be cloned and parallel tasks can use Git worktrees, with cleanup as needed. Official Git documentation confirms worktrees provide multiple working directories for one repository.

What the mechanism does not establish is whether the agent chose the intended repository, whether two changes conflict, or whether the repository owner approved a release. Each repo should keep its own CI, PR, identity and authorization controls. A home map can improve navigation without weakening that contract.

Scale by disclosing the relevant map

At 04:42, Pocock describes flat links as manageable for tens of repositories, not hundreds. His next step is still simple: point at domain-specific files and open only the relevant area. He explicitly prefers a monorepo when feasible; the home pattern suits organizations that cannot combine public/private or separately governed projects.

A count threshold is a heuristic, not a benchmark. The useful test is selection accuracy: can an agent identify the owning project and fetch the correct instruction file, without repeatedly consuming irrelevant context? At scale, routing and data classification become more consequential than the number of Markdown files.

Shared tooling expands capability and blast radius

At 05:43, Pocock tours a personal Markdown wiki and tools that reach services including Gmail, Slack, Discord, YouTube, GitHub and calendars. He says the centralized environment lets him combine knowledge retrieval, repo work and business tasks in one session. These are creator-reported uses, not an independent audit of permissions or outcome quality.

For GhostMesh this is the real architectural tension. A shared home repo can expose helpful tools and documented procedures, but it must not convey permission just by naming those tools. Service credentials, delegated scope, human approvals and audit evidence still belong at the destination. The most useful implementation centralizes knowledge and navigation while keeping execution authority enforceable and separately revocable.

The strongest objection: a central map can also rot

If a home repo becomes a second copy of every repo's instructions, it defeats its own premise. A broad tool catalog may add context noise, while stale paths and shared files can become silent operational dependencies. Making every team use one home repo without testing its actual harness behavior could simply move friction to a new location.

Start with a small, reviewed index and an ordinary cross-repo task. Measure wrong-repo navigation, duplicated skill maintenance, stale instructions and reviewer interventions. A home repo that makes tasks easier without relaxing permissions earns its place. A home repo that requires a new control plane does not.

An experiment without another platform

Select one authorized cross-repository task and compare the current launch setup with a read-only home index. Keep model, code revisions, task and permissions consistent. Measure correct repo discovery, instructions retrieved, change scope, reviewer effort and owner interventions. Do not introduce credentials or production deployment rights as part of the test.

If the home repo reduces duplicate guidance and the agent selects the right target with no scope regression, retain it. If it adds stale assumptions or makes permissions less inspectable, prefer the existing per-repo workflow.
