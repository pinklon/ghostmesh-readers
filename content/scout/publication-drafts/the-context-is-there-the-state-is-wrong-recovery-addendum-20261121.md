### A valid backup can still restore yesterday’s state

When an agent recovers after a crash, it needs to know whether a message was only prepared or already sent. That question depends on more than whether a database opens. An older, structurally sound file can give the agent the wrong answer about what it should do next.

We checked the distinction with a disposable SQLite database and a single invented dispatch. SQLite’s write-ahead log holds recent committed changes before they are copied into the main database file. We saved the prepared state in that main file, then committed a simulated sent state while the database remained open in write-ahead logging mode. Both the main-file-only copy and the SQLite backup snapshot passed the database’s integrity check. The first still said prepared. The snapshot said sent, matching the live database. No message was sent. [SQLite’s write-ahead logging notes](https://sqlite.org/wal.html#the_wal_file) and [backup documentation](https://sqlite.org/backup.html) explain why the two copies can differ.

The judgment is practical: require a recovery test to check the last consequential state transition, not just file integrity. A clean shutdown, a correctly coordinated snapshot, or a different journal mode changes the example; this does not indict every file copy. And even a correct local snapshot cannot tell you whether a remote service accepted a send that happened just before the crash. If you can’t reconcile the local record with an external receipt, hold the action instead of automatically replaying it. [AWS’s outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#issues-and-considerations) makes the related point that recording an event and processing it only once are separate guarantees.

Reversible check for your own system: on a throwaway copy with sending disabled, restore through the usual backup path. Compare the recovered last event ID and action state against a known baseline, then try a case with a missing receipt. It should stay unresolved, not be queued to send again.
